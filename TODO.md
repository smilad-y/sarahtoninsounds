A shared `.jp-page` wrapper (holding the `max-width:1492px; margin:0 auto` that `.jp-stage` used to carry alone) is needed so that margin percentage resolves against the right width.
  - **Two real implementation bugs hit and fixed along the way** (both empirically confirmed via isolated throwaway test pages before being trusted, not just reasoned about):
    1. An absolutely-positioned `<img>` with `top`+`bottom` both set and `height: auto` **ignores `bottom` entirely** and sizes itself from its own intrinsic aspect ratio instead — confirmed side-by-side against a plain wrapper `<div>` carrying the same `top`+`bottom` (which correctly stretches). So whenever 2:78 is repositioned, it must be a plain wrapper div containing the `<img>` (the `<img>` filling it at `width:100%; height:100%; object-fit:cover`), never `top`+`bottom` on the `<img>` directly.

Root cause: `.jp-stage`'s decorative children carry explicit `z-index` values (1, 3, 4, 5, 6, 7, 8, 15, 18, 20), and neither `.jp-stage` nor `.jp-page` contains/isolates that range — so anything placed as a sibling that visually overlaps `.jp-stage` (like `.jp-body-region`, via the negative margin-top) gets compared directly against all of those numbers in the same ambient stacking context. A hand-picked `z-index: 10` on `.jp-body-region` "fixed" it once by luck (clearing 1–8) but is fragile and not principled — and a second attempt's `background-color` fallback on the now-higher-stacked region additionally painted over the stage's yellow paper/megaphone/stars in the overlap zone (fixed by removing that fallback; `body`'s own `base.css` background is already the same cream, so nothing is lost below the fold).
  - **Proposed cleaner technique (validated only in an isolated scratch test, e.g. `isolation-test/test.html` — NOT yet applied to the real page)**: add `isolation: isolate;` to `.jp-stage`'s existing rule. This contains `.jp-stage`'s entire internal z-index range so it never needs to be compared against anything outside it — a later, plain DOM sibling (`.jp-body-region`, no z-index of its own needed at all) then naturally paints on top via ordinary DOM order. Confirmed in isolation: a test container with children at z-index 1, 8, and 20 plus `isolation: isolate`, followed by a plain later sibling with no z-index, correctly showed the sibling painting above all three, including the z-index:20 one. This removes the need to hand-pick/maintain a z-index number against `.jp-stage`'s internal layers (currently 10 different values across nav/title-block/decor, and growing).
